# 数字で見る、話題の企業 — 週次公開 手順書（COMPANY_GUIDE.md）

クラウドルーティン **company-weekly-auto** が毎週読む正式手順書。**週1本**、いま出来高や値動きで話題になっている企業を、**一次情報の数字と歴史**で深掘りする。コンプラ＆品質ゲートを通れば自動公開、危ういものは公開せずエスカレ。
**人が編集する＝SYNC_FILES入り。** ⚠️ 発火エンジン・signal_lab系・固定オラクル・6コアHTMLには触れない（実行のみ）。

> 発足の経緯: 2026-08-31、オーナー要望「**今話題の企業の深掘り記事。歴史や今後の展開、いろいろなデータを示して将来性はどうなのか**」。
> ⚠️ **「将来性」は、このサイトで最も慎重に扱うべき題材**（無登録の投資助言に最も近い）。
> **本シリーズはその要望に、「判断を書く」ではなく「判断できる材料を全部そろえて渡す」で答える。**
> 🔑 **もうひとつの狙い＝このレーンは枯渇しない。**題材をサイト自身のランキングデータから機械的に選ぶので、
> 相場が動く限り候補が尽きない（格言シリーズが44本で汲み尽くしたのとは構造が違う）。

## 0. このシリーズの狙いと、絶対に越えない線

**狙い＝読者が「この会社の将来性を、自分で見積もれる」状態にすること。**
そのために渡すのは、①事実の数字 ②会社自身が公表しているリスク ③見方が割れている論点の両側 ④**次に何が出れば見方が変わるか**。

🚨 **このシリーズ専用の禁止事項（1つでも触れたら公開しない）:**

- **目標株価を書かない。**
- **買い・売り・保有の推奨を書かない。**「〜は外せない」「ポジションを抑えて」「押し目は好機」等の助言表現も同じく禁止。
- **「割安」「割高」と断定しない。**PER・PSR等の数字と比較対象は出してよいが、**評価語で締めない**。
  ⭕️「PER は◯倍で、同業◯社の中央値は◯倍でした（2026-XX-XX 時点）」／❌「むしろ割安水準」
- **将来の業績・株価を予測しない。**会社が出した予想は「**会社がこう公表している**」として引くだけ。
- **証券会社名を列挙しない**（買い方の案内はしない）。
- **1回1社**。同じ会社を本レーンで続けて書くのは**90日あけてから**（ローテーション確保のため。§2-1手順3）。
  🔑 ⚠️ **これは「既刊とかぶるな」という意味ではない。**発足前の既刊（`guide-nvidia-2026-05.html` 等）や
  大きな動きがあった会社は、**続報として書いてよい**（§1⓪を必ず付ける・2026-08-31 オーナー指示）。
- **急騰・急落の当日と翌日には書かない**（下の§2-2）。**煽り記事にしない**ことがこのシリーズの生命線。

🚨🚨 **既存の企業記事をテンプレにしないこと。**
`guide-nvidia-2026-05.html` / `guide-toyota-2026-05.html` / `guide-tsmc-2026-05.html` / `guide-kioxia-*.html` /
`guide-softbank-group-2026-05.html` / `guide-amd-2026-05.html` / `guide-oriental-land-2026-06.html` は
**2026年5〜6月に書かれたもので、今のコンプラゲートなら通らない表現を含む**
（実例＝「これはむしろ**割安**水準」「AI を信じるなら **NVDA は外せない**」「2026 年は**強気継続でほぼ確定**」
「ポジションサイズを抑えて」「SBI 証券・楽天証券・マネックス証券」）。
**構造の手本は `guide-proverb-atama-shippo.html`**（nav・免責・SVG の作り）だけにする。

## 1. 記事の構成（この順に・全部埋まらなければ公開しない）

0. **前回の記事のその後**（🆕 2026-08-31 オーナー指示。**その会社の既刊がある場合のみ・必須**）

   > 「銘柄はかぶってもいいと思います。前回と今回じゃ状況が違いますし、**むしろあの後どうなったのかというのも
   > 気になります**。銘柄がダブる場合は**前回どうだったのかという前置きをしてから、今回はこういう状況だ**という
   > 記事を書いてもらえれば、それはそれで面白いと思います」

   🔑 **重複は避けるものではなく、続報にすると価値が上がる。**この節を冒頭に置く。
   - 既刊の**記事名・公開日・リンク**（「2026年5月時点の記事です」と**時点を明示**）
   - **前回時点の数字を3つ**（既刊から引く）→ **いまの数字**（一次情報＋確認日）→ 並べて差分が見えるようにする
   - **その間に起きたこと**を3〜5件の箇条書き（各行に**出典と日付**。決算・開示・公的統計から）
   - 🚨 **既刊から引いてよいのは「事実・数字・公開日」だけ。**評価語や見立て（「本命銘柄」「割安水準」等）は
     **引用しない**。引用すると、いまのゲートで禁じている表現をこの記事が再生産することになる
   - 🚨 **「前回の見立てが当たった／外れた」を書かない。**答え合わせは的中率の主張になり、§0④に触れる。
     書くのは**「前回はこの数字だった → いまはこの数字」**という事実の対比だけ

1. **どんな会社か** — セグメント別の売上構成。**一次情報から**（決算短信 or 有価証券報告書）。図1枚（構成比）
2. **歴史** — いつ何で伸び、何で躓いたか。**事実の年表**（各行に出典と年）。⚠️ 物語にしない・原因を断定しない
3. **直近の決算の数字** — 売上・各利益・前年同期比・会社予想と進捗率。**すべて一次情報＋確認日**
4. **会社自身が挙げているリスク** — 有価証券報告書「事業等のリスク」から**3〜5件を要旨で**紹介し、原文へリンク。
   🔑 **ここがこのシリーズの芯。**書き手の推測ではなく**会社の自己申告**なので、価値が高くコンプラ上も最も安全
5. **上がる材料／下がる材料**（この記事の主役・2026-08-31 オーナー指示で形を確定）
   > 「将来性というのは、上がるか下がるかということではなく、**上がる可能性がある材料はどういうことなのか、
   > 下がる可能性がある材料はどうなのか**、というのを表示しておけば、あとは投資判断は本人で」

   **左右に対で並べる**（表かカードで、視覚的に対等に）。⚠️ **数を揃える**（片側だけ厚いと、それ自体が誘導になる）。
   - 各材料に必ず添える3点＝**①出典（誰が・どの資料で言っているか）②確認日 ③それが効くとどうなるか**
   - ⚠️ **書き手の意見を混ぜない。**「材料」として立てられるのは、会社の開示・公的統計・
     報道で確認できる事実だけ。⭕️「会社は次期の設備投資を◯億円と公表した（出典・確認日）」／
     ❌「需要は当面続くとみられる」
   - ⚠️ **どちらが重いか、という重み付けをしない。**並べるところまでが記事の仕事。
   - ⚠️ **結論の文を書かない。**「以上が、いま公開情報から拾える材料です。どう見るかはご自身で」で閉じる
6. **これから何を見れば分かるか** — 次の決算発表日（`earnings-calendar.json` と会社IRで確認）・
   そのとき見る数字・どの開示に出るか。**読者が自分で見方を更新できる形にする**
7. **まとめ＋関連ガイド** — ⚠️ まとめで結論を出さない。「見るべき指標はこの3つ」で終える

- **インラインSVGの図を2枚以上**（セグメント構成／業績の推移）。ライト/ダーク両対応・`※概念を示すイメージ図です`。
- 冒頭 `disclaimer-banner`、本文末とフッターに `data-disclaimer="kinsho-v1"`、nav10ボタンで `guides.html` を current。
- ファイル名：`guide-company-<コード小文字>-<英字略称>.html`
  - 日本株はコード＝証券コード（例 `guide-company-285a-kioxia.html`）、**海外株はティッカー**（例 `guide-company-nvda-nvidia.html`）
  - ⚠️ **同じ名前が既にあるときは末尾に `-<YYYY-MM>` を足す**（例 `guide-company-nvda-nvidia-2026-11.html`）。
    既存記事は**絶対に上書きしない**（続報は別ファイル）

## 2. 毎週の手順

### 2-1. 候補を機械的に選ぶ（恣意的に選ばない）

⚠️ **「話題」を人の感覚で決めると提灯記事に見える。**サイト自身のデータで定義し、**その基準を記事にも明記する。**

🌏 **日本株と海外株の両方を扱う**（2026-08-31 オーナー指示）。
> 「海外の企業のことも、やっぱり**日本株に大きく影響を与える**ので、注目されている銘柄はぜひ記事にしてほしい」

**1. 今週どちらを書くか決める（偏らせないため）**

`COMPANY_LEDGER.md` の**最新1件**を見て、**前回と違うほう**を今週の第1候補にする（前回が日本株なら今週は海外株）。
台帳が空＝初回は**日本株**から。⚠️ 第1候補側に候補が無ければ、もう一方から選んでよい（無理に空振りしない）。

**2. 候補を機械的に選ぶ（恣意的に選ばない）**

⚠️ **「話題」を人の感覚で決めると提灯記事に見える。**サイト自身のデータで定義し、**その基準を記事にも明記する。**

- **日本株**＝`jp-rankings.json`（`jp-rankings.yml` が平日夕方に生成）の **直近14日ぶん**を `git log` で遡り、
  `gainers` / `losers` / `hot` のいずれかに **2回以上**登場した銘柄。

  🆕 **2026-09-02〜：この選定は `edinet-yuho.json` の `candidates[]` に機械化済み。**まずそれを読む（同じ定義・
  `fallback: true` なら「2回以上の該当なし・最新 hot のみ」）。以下の git log 手順は JSON が無い／古いときの予備。

  🚨 **先に履歴を伸ばすこと（2026-09-01 実測）。**クラウドのクローンは **shallow（50コミット）**で、
  そのままだと `git log -- jp-rankings.json` が**1件しか返らない**（14日分を見ているつもりで見えていない）。

  ```
  timeout 100 git fetch --depth=500 origin main
  ```

  ⚠️ **`git fetch --unshallow` は使わない**——2026-09-01 の実測で**2分でタイムアウトした**。
  `--depth=500` なら約20秒で 692コミット（＝約8日分）取れた。
  ⚠️ このリポジトリは**1日あたり80〜90コミット**あるので、`--depth=500` でも14日には届かない。
  **必要なら深さを増やす**（`--depth=1500` 程度）。取れた範囲を台帳に書くこと。

  ⚠️ **`jp-rankings.json` は毎日は更新されない。**2026-09-01 の実測で、取れた範囲（8/24〜9/1）に
  更新は **3回だけ**（8/26・8/28・8/29）。**「2回以上登場」は思ったより薄いデータの上に乗っている。**

  📌 **候補が0件になったときの受け皿**＝「2回以上」で誰も残らなければ、
  **最新スナップショットの `gainers` / `losers` / `hot` の上位**から候補にしてよい。
  ただし**台帳に「2回以上の該当なし・最新1回のみで選定」と必ず書く**（基準を下げたことを隠さない）。
  🔑 それでも `hot`（出来高急増）に入っていることが条件＝**サイト自身のデータで「話題」を定義する**原則は崩さない。
- **海外株**＝次の順で探す。
  - ① `earnings-calendar.json` の `us` で、**決算発表日が「2営業日前 〜 14日前」**の会社
    （🔑 決算が出た直後＝数字が揃っていて、この「数字で見る」シリーズと最も相性がよい）。
  - ② ①が空なら、**直近15〜60日**の `guide-news-*.html` と `drafts/news/NEWS_LEDGER.md` で
    **主役として扱われた海外企業**（このとき記事から**必ずその速報へリンクする**）。
  - ⚠️ **どちらも「サイト自身のデータ」から取る。**外から適当に有名企業を持ってこない
    （それをやると選定が恣意的になり、提灯記事と区別がつかなくなる）。
  - ⚠️ **個別海外企業のランキングは、このリポジトリに存在しない**（2026-08-31 実測。
    `hot-assets` は米国セクターETF、シグナルの universe 18銘柄も個別株なし）。だから上の2つで代用している。

**3. 本レーンで最近書いた会社を外す（ローテーション確保）**

`COMPANY_LEDGER.md` に**90日以内**の記載がある会社を外す。
⚠️ ただし**大きな動きがあれば90日以内でも続報を書いてよい**（決算・M&A・業績修正など。台帳に理由を1行）。

**4. 既刊があっても外さない。続報として書く（🆕 2026-08-31 オーナー指示で方針を反転）**

> 「銘柄はかぶってもいいと思います。前回と今回じゃ状況が違いますし、むしろあの後どうなったのかというのも
> 気になります」

     重ねずに繋ぐ）。

ニュース側の重複確認の結果）を**記事と台帳の両方に書く**。
⚠️ **候補が全部消えた週は、無理に書かずに台帳へ「候補なし・理由」を1行書いて終了する。**

### 2-2. 一次情報を先に取る（取れなければ書かない）

🚨 **この表はクラウド実行環境での実測（2026-09-01・初回実行）。手元PCの結果とは違う。**
手元では全部200でも、クラウドでは経路が塞がっていることがある。**毎回、着手前に curl で測り直して台帳に書くこと。**

**海外株（米国）— 安定して取れる**

| 何を取るか | どこから | クラウド実測 |
|---|---|---|
| 提出書類の一覧（10-K / 10-Q / 8-K） | `data.sec.gov/submissions/CIK<10桁ゼロ埋め>.json` | ✅ **200** |
| 書類の本文 | `www.sec.gov/Archives/edgar/data/<CIK>/<accession>/<file>.htm` | ✅ **200** |

- 🔑 **§1④「会社自身が挙げるリスク」の米国版は 10-K の "Item 1A. Risk Factors"。**
  有価証券報告書「事業等のリスク」と同じ役割で、**会社の自己申告**なので同じ扱いができる。
  §1②の年表に使える訴訟・規制の事実は **10-K "Item 3. Legal Proceedings"** にある。
- ⚠️ **SEC は User-Agent に連絡先を名乗ることを求めている。**サイト名とドメインを名乗る形にすること
  （例 `marketwatch-jp (https://marketwatch-jp.com)`）。**付けないと403**（実測）。
  🚨 **個人のメールアドレスは絶対に書かない。**
  🔑 これは**UA偽装ではない**——「ブラウザのふりをして bot 判定を迂回する」のは禁止のままで、
  「求められた通り自分の身元を名乗る」のは別物。名乗っても弾かれるなら**エスカレして止まる**。

**日本株 — 有価証券報告書は `edinet-yuho.json` から読む（2026-09-02 解決）**

🔑 **routine は EDINET API を直接叩かない。**クラウド routine は GitHub Secrets を読めないので API v2 は必ず 401 になる
（2026-09-01 の実測）。代わりに Actions `edinet-yuho.yml`（平日 19:40 JST・`build_edinet_yuho.py`）が
`EDINET_API_KEY`（edinet-holdings と同じキー・**登録済み**）で取得して **`edinet-yuho.json` にコミット**しておく
（fundamental-context.json と同じ「Actions が取って置く」型）。**手順＝このファイルを開くだけ。**

| キー | 中身 |
|---|---|
