# 数字で見る、話題の企業 — 週次公開 手順書（COMPANY_GUIDE.md）

クラウドルーティン **company-weekly-auto** が毎週読む正式手順書。**週1本**、いま出来高や値動きで話題になっている企業を、**一次情報の数字と歴史**で深掘りする。コンプラ＆品質ゲートを通れば自動公開、危ういものは公開せずエスカレ。
**人が編集する＝SYNC_FILES入り。** ⚠️ 発火エンジン・signal_lab系・固定オラクル・6コアHTMLには触れない（実行のみ）。

> 発足の経緯: 2026-08-31、オーナー要望「**今話題の企業の深掘り記事。歴史や今後の展開、いろいろなデータを示して将来性はどうなのか**」。
> ⚠️ **「将来性」は、このサイトで最も慎重に扱うべき題材**（無登録の投資助言に最も近い）。
> **本シリーズはその要望に、「判断を書く」ではなく「判断できる材料を全部そろえて渡す」で答える。**
> 🔑 **もうひとつの狙い＝このレーンは枯渇しない。**題材をサイト自身のランキングデータから機械的に選ぶので、
> 相場が動く限り候補が尽きない（格言シリーズが44本で汲み尽くしたのとは構造が違う）。

## 0. このシリーズの狙いと、絶対に越えない線

**狙い＝読者が「この会社の将来性を、自分で見積もれる」状態にすること。**
そのために渡すのは、①事実の数字 ②会社自身が公表しているリスク ③見方が割れている論点の両側 ④**次に何が出れば見方が変わるか**。

🚨 **このシリーズ専用の禁止事項（1つでも触れたら公開しない）:**

- **目標株価を書かない。**
- **買い・売り・保有の推奨を書かない。**「〜は外せない」「ポジションを抑えて」「押し目は好機」等の助言表現も同じく禁止。
- **「割安」「割高」と断定しない。**PER・PSR等の数字と比較対象は出してよいが、**評価語で締めない**。
  ⭕️「PER は◯倍で、同業◯社の中央値は◯倍でした（2026-XX-XX 時点）」／❌「むしろ割安水準」
- **将来の業績・株価を予測しない。**会社が出した予想は「**会社がこう公表している**」として引くだけ。
- **証券会社名を列挙しない**（買い方の案内はしない）。
- **1回1社**。同じ会社は**180日以内に書き直さない**。
- **急騰・急落の当日と翌日には書かない**（下の§2-2）。**煽り記事にしない**ことがこのシリーズの生命線。

🚨🚨 **既存の企業記事をテンプレにしないこと。**
`guide-nvidia-2026-05.html` / `guide-toyota-2026-05.html` / `guide-tsmc-2026-05.html` / `guide-kioxia-*.html` /
`guide-softbank-group-2026-05.html` / `guide-amd-2026-05.html` / `guide-oriental-land-2026-06.html` は
**2026年5〜6月に書かれたもので、今のコンプラゲートなら通らない表現を含む**
（実例＝「これはむしろ**割安**水準」「AI を信じるなら **NVDA は外せない**」「2026 年は**強気継続でほぼ確定**」
「ポジションサイズを抑えて」「SBI 証券・楽天証券・マネックス証券」）。
**構造の手本は `guide-proverb-atama-shippo.html`**（nav・免責・SVG の作り）だけにする。

## 1. 記事の構成（この順に・全部埋まらなければ公開しない）

1. **どんな会社か** — セグメント別の売上構成。**一次情報から**（決算短信 or 有価証券報告書）。図1枚（構成比）
2. **歴史** — いつ何で伸び、何で躓いたか。**事実の年表**（各行に出典と年）。⚠️ 物語にしない・原因を断定しない
3. **直近の決算の数字** — 売上・各利益・前年同期比・会社予想と進捗率。**すべて一次情報＋確認日**
4. **会社自身が挙げているリスク** — 有価証券報告書「事業等のリスク」から**3〜5件を要旨で**紹介し、原文へリンク。
   🔑 **ここがこのシリーズの芯。**書き手の推測ではなく**会社の自己申告**なので、価値が高くコンプラ上も最も安全
5. **上がる材料／下がる材料**（この記事の主役・2026-08-31 オーナー指示で形を確定）
   > 「将来性というのは、上がるか下がるかということではなく、**上がる可能性がある材料はどういうことなのか、
   > 下がる可能性がある材料はどうなのか**、というのを表示しておけば、あとは投資判断は本人で」

   **左右に対で並べる**（表かカードで、視覚的に対等に）。⚠️ **数を揃える**（片側だけ厚いと、それ自体が誘導になる）。
   - 各材料に必ず添える3点＝**①出典（誰が・どの資料で言っているか）②確認日 ③それが効くとどうなるか**
   - ⚠️ **書き手の意見を混ぜない。**「材料」として立てられるのは、会社の開示・公的統計・
     報道で確認できる事実だけ。⭕️「会社は次期の設備投資を◯億円と公表した（出典・確認日）」／
     ❌「需要は当面続くとみられる」
   - ⚠️ **どちらが重いか、という重み付けをしない。**並べるところまでが記事の仕事。
   - ⚠️ **結論の文を書かない。**「以上が、いま公開情報から拾える材料です。どう見るかはご自身で」で閉じる
6. **これから何を見れば分かるか** — 次の決算発表日（`earnings-calendar.json` と会社IRで確認）・
   そのとき見る数字・どの開示に出るか。**読者が自分で見方を更新できる形にする**
7. **まとめ＋関連ガイド** — ⚠️ まとめで結論を出さない。「見るべき指標はこの3つ」で終える

- **インラインSVGの図を2枚以上**（セグメント構成／業績の推移）。ライト/ダーク両対応・`※概念を示すイメージ図です`。
- 冒頭 `disclaimer-banner`、本文末とフッターに `data-disclaimer="kinsho-v1"`、nav10ボタンで `guides.html` を current。
- ファイル名：`guide-company-<証券コード小文字>-<英字略称>.html`（例 `guide-company-285a-kioxia.html`）

## 2. 毎週の手順

### 2-1. 候補を機械的に選ぶ（恣意的に選ばない）

⚠️ **「話題」を人の感覚で決めると提灯記事に見える。**サイト自身のデータで定義し、**その基準を記事にも明記する。**

1. `jp-rankings.json`（`jp-rankings.yml` が平日夕方に生成）の **直近14日ぶん**を `git log` で遡り、
   `gainers` / `losers` / `hot` のいずれかに **2回以上**登場した銘柄を候補にする。
2. `drafts/company/COMPANY_LEDGER.md` に**180日以内**の記載がある銘柄を外す。
3. **ランキング入りの直近日から中3営業日あいていない銘柄を外す**（急騰の熱が残っているうちは書かない）。
4. 🚨 **ニュースレーンと重ならないか必ず確認する（2026-08-31 オーナー指示）。**
   デイリーニュース記事（`news-daily`／手順書 `drafts/NEWS_DAILY_GUIDE.md`）は
   **個別銘柄のニュース（決算・新製品・M&A・不祥事・急騰急落）を対象に含む**ので、放っておくと同じ会社を
   同じ週に2本書くことになる。実例＝`guide-news-2026-08-02-apple-q3-earnings-drop` /
   `guide-news-2026-08-14-applied-materials-q3-ai-demand`。
   - **直近14日の `guide-news-*.html` と `drafts/news/NEWS_LEDGER.md` を見て、同じ会社が扱われていたら
     その週は選ばない**（次の候補へ送る）。台帳に「ニュース側と重複のため見送り＋記事名」を1行残す。
   - 14日より前に扱われていた会社は**書いてよい。ただし記事から必ずその速報へリンクする**
     （🔑 **役割が違う**＝ニュース＝「その日に何が起きたか」／本シリーズ＝「この会社は何で稼ぎ、材料は何か」。
     重ねずに繋ぐ）。
5. 残った中から**時価総額の大きい順**に1社。⚠️ 選定の理由（何日にどのランキングに何回入ったか・
   ニュース側の重複確認の結果）を記事と台帳に書く。

### 2-2. 一次情報を先に取る（取れなければ書かない）

- 決算短信・有価証券報告書＝`disclosure2.edinet-fsa.go.jp`（EDINET）/ `release.tdnet.info`（TDnet）/ 各社IR。
  統計は `jpx.co.jp`。**2026-08-31 に手元から3件とも200を実測**。🚨 **クラウド側は別。初回に測って台帳へ書くこと。**
- **決算短信と有報の両方に届かなければ、その週は書かずにエスカレする。**二次情報で企業を語らない。
- 遮断の種類を台帳に書き分ける＝`CONNECT tunnel failed`＝**経路（許可リスト）**／`cf-mitigated` 付き403＝**先方のbot判定**。
  ⚠️ **UA偽装での迂回はしない。**

### 2-3. 書く → ゲート → 公開

4. §1の構成で `guide-company-<code>-<name>.html` を作成。
5. 【コンプラ自動公開ゲート】Agentツールで **model=opus** のサブエージェント（Read,Edit・`.claude/agents/compliance-reviewer.md` ペルソナ）に監査させる：①黒/グレー/白 ②グレーは軽微修正（表現軟化・免責追加のみ／事実・数値・SVG・構造は不変）をEditで適用 ③再読し最終判定 ④黒 or 要協議なら編集せず「エスカレ」。
   🚨 **監査役へ渡すときに「§0の禁止事項6点」を明示的に読ませること**（一般のコンプラ観点だけだと、助言表現を見逃す）。
6. 【品質】`QUALITY_RUBRIC.md` の5観点で自己採点。⚠️は表現・補足1文だけ自己修正、❌はエスカレ。
7. **公開判定**：初期=白 もしくは（グレー→軽微修正→最終=白）かつルーブリック合格のときのみ。別の fresh な **model=opus**（Readのみ・同ペルソナ）で独立確認。
   【決定論チェック（全部／欠けたら手順9）】① `kinsho-v1` が冒頭＋本文末＋フッター ②禁止語なし（必ず/絶対/確実/100%/儲かる/一択/今すぐ買い/割安/割高/外せない/好機）③**目標株価が本文に無い** ④買い・売り・保有の推奨が無い ⑤**数字すべてに一次情報のURLと確認日** ⑥SVG「概念図」明示。
8. **公開**：
   - a. `python publish_article.py --file guide-company-<code>-<name>.html --category "数字で見る企業" --emoji 🔬 --card-title "<社名>" --desc "<1行説明>"`
   - b. `python check_site_consistency.py; echo EXIT=$?`（赤なら中止しエスカレ）
   - c. `git add guide-company-*.html guides.html generate_market_news.py sync_to_github.py drafts/ && git commit -m "feat: 数字で見る企業 auto-publish <code>" && git push origin main`
   - d. `drafts/company/COMPANY_LEDGER.md` に「✅公開済み・社名・証券コード・**選定の根拠（ランキング登場日）**・一次情報URLと確認日・コンプラ判定」を追記しコミット＆push。
9. **エスカレ（公開しない）**：`drafts/company/draft-<code>.html` に `noindex,nofollow` 付きで保存し、`COMPANY_LEDGER.md` に「🚩要人間レビュー（理由）」を記録して push。
   > 🔒 **🔴黒と判定した本文はリポジトリにコミットしない**（public リポジトリで raw から読めるため）。台帳には日付・対象・理由の要約だけ。
10. 日本語要約：選んだ会社と選定根拠・一次情報の到達可否・コンプラ判定・公開有無・ファイル名。

## 3. 絶対厳守

- **週1本まで。**候補が無い週は**書かない**（台帳に「候補なし・理由」を1行）。無理に埋めない。
- **一次情報に届かなければ書かない。**
- **§0の禁止事項6点は、1つでも触れたら公開しない。**
- 6コアHTML・political-feed・track-record・sitemap.xml に直接触れない。発火エンジン・signal_lab系・固定オラクルは書き換えない（実行はOK）。
- **情報提供であり投資助言ではない。**迷いがあれば公開せずエスカレ（安全側）。

## 4. 番人の扱い（他のレーンと違う点）

⚠️ **このレーンは題材キューを持たないので、`check_automation_health.py` の `QUEUE_LANES` では見張れない**
（キューが無い＝枯渇しないのが設計）。代わりに **`COMPANY_LEDGER.md` の最終更新の鮮度**で見張ること。

🚨 **レーンを足したら必ず何かで見張る**——2026-08-31 に、格言5日・詐欺7日の枯渇を誰も知らないまま放置した原因は
「番人に登録する手順が無かった」ことだった。
