# 検算の関門（研究の数字の間違いを見つける仕組み）設計書

作成: 2026-11-26 / 対象: 研究の道具（`*_lab.py` など）と、その結果を使うところ（リスト・研究の地図・DOCTRINE・朝のメール）

〔Claude の判断〕と書いた所は、オーナーに聞かずに Claude が決めたこと。読んで違えば直す。

## 1. 目的となぜ

オーナーの言葉＝「過去検証の測り間違いはどのくらいの頻度、どのくらいのパーセンテージで起きていますか」→「間違いを見つける仕組みを作ってください」→ 洗い直す範囲は「今後＋使用中を洗う」→ 作り方は「案1（関門型）」。

ねらい＝**研究の結果を、そのまま信じてよい状態にする**。いちばん害が大きいのは**偽の合格**（間違いが良い成績を作り、それを使ってしまう）。

### 出発点（2026-11-26 実測・PILLAR_PREREG.md と SESSION_ARCHIVE.md から）

| 項目 | 値 |
|---|---|
| 結果が書かれている登録（9/27〜11/26） | 約112件 |

| わざと壊すテスト | 道具ごとに手で作っている |
| 別の書き方での突き合わせ | OJ3 の1回だけ（確かめ側の境目の書き間違いを1件見つけた） |

過去の6件：M1・M5-1（MT5 の2022年5月より前の欠陥データ＝回数が3〜4倍に）／ST ラウンド1（NY17時の切り替わりの費用）／R1（Yahoo のドル円の偽の値・1306.T の10倍ずれ）／RV（損切りの確かめが片側だけ＝1回で −694R）／CP（突き合わせの番号の誤り）／Yahoo の株式分割の直しもれ。その前（6〜7月）にも、利確2の数え漏れ・同じ日の合図を別々に数えた誤り・偽薬の作りの誤り（合格の基準を満たしたのに取り消し）があった。

**見えていないもの**：もっともらしい数字になる間違いは、今の見つけ方（ありえない数字に気づく）では見えない＝本当の割合は5%より多いかもしれない。

### 成功条件

1. 過去の6件の型（作った見本のデータ）を、点検が全部見つける
2. 今ある取引の一覧で、誤報がほとんど出ない（較正の表を残す）
3. 新しい道具は、点検を通らないと結果を書けない
4. 「合格」は、別の書き方で数え直して1件ずつ一致した記録がないと、どのリストにも合格として載らない
   - 自動で出る合格（シグナル研究の昇格など）も、数え直すまではメールの絞りや EA への橋渡しに使われない（2026-11-27 オーナー決定）
5. いま使っている結果（約13件）を数え直し、一致したか・食い違いの中身をオーナーに報告する
6. 点検は損益の合計・平均・勝率を見せない（事前登録の「結果を見る前」を壊さない）

## 2. やること・やらないこと・失敗とみなすこと

**やること**：3つの部品（点検・数え直し・わざと壊す）／止める関門／いま使っている結果の洗い直し

**やらないこと**
- 過去の約112件をすべて洗い直すこと（オーナーが「今後＋使用中」を選んだ）
- 今日より前の約200本の道具を書き換えること（使っているものだけ、数え直しで見る）
- 固定の検査（`signal_lab_verify.py`・`check_guide_draft.py`・`check_plain_japanese.py`・`exit_lab_verify.py`）を編集すること
- 間違いが見つかった目印を、自動でメールや決まりから外すこと（外すかはオーナーが決める）

**失敗とみなすこと**（技術的に動いていても）
- 点検が、run の前に結果（損益・判定）を漏らす
- 誤報が多くて、鳴っても誰も見なくなる
- 過去の判定を黙って書き換える（訂正はいつも追記）
- 毎日の自動の仕事（Actions・routine）を止める
- 数え直しの担当が元の道具のコードを読んで写す（独立でなくなる）

## 3. 制約

- 事前登録：run は1回だけ。読み込みや計算の誤りを直すときだけやり直してよい（理由を登録に書く）
- `research/` は送らない。手元は git ではない（`auto_pull.py` の ZIP でそろえる）
- 価格と J-Quants の数字は公開しない＝取引の一覧は手元だけ。送るのは要約と指紋だけ
- 新しい番人は、入れる前に過去の全件で誤報を測る（SESSION_ARCHIVE の教訓）
- 費用：数え直しは担当1回分かかる＝合格と使用中だけにする
- 決まりはコードで守る。閾値は1か所だけに書く（単一の真実）
- テストは `tests/`（根の道具）・`research/` の道具は同じ場所の `test_*.py`

## 5. 仕組み

```
登録 → 道具で数える →【① 点検】→ 結果を書く
                      │ error なら書かずに止まる（損益は見せない）
                      ↓ 判定が合格側／良すぎる印／いま使っている
                【② 数え直し】登録の文だけから別の担当が数える
                      ↓ 1件ずつ突き合わせ・食い違いは全部説明
                「検算済み」の記録 → リストに合格として載る

新しい道具を作るとき：【③ わざと壊す】で、テストが気づかない壊し方を一覧にして登録に書く
```

### 5.1 取引の一覧の共通の形

| 欄 | 中身 |
|---|---|
| study | 研究の名前（例 `OJ5`） |
| market | `fx`／`jp`／`index`／`commodity`／`crypto` |
| symbol | 銘柄 |
| side | 買い `1`／売り `-1` |
| signal_time | 合図が確定した時刻（任意・UTC） |
| entry_time・exit_time | 建てた時刻・決済した時刻（UTC・ISO） |
| entry_price・exit_price | 建値・決済の値 |
| stop_price | 損切りの値（任意） |
| unit | `pips`／`pct`／`bp` |
| gross・cost・net | 費用前・費用・費用後（unit の単位） |
| r | 損切りの幅で割った費用後（任意） |
| exit_reason | 出た理由（`tp`・`sl`・`time` など） |
| period | 期間の名前（任意・`A`・`B`・`C` など） |

- 道具は自分の一覧からこの形への変換を数行で書く（`to_common()`）
- 保存は手元だけ（価格を含むため）

**取引でない結果（目印・ゲート）の形**〔Claude の判断〕：目印や危険スコアのように「どの株のどの日に印が付いたか」を比べる研究は、取引の形が合わない。そこで2つ目の形を使う＝`study`・`market`・`symbol`・`date`・`flag`（どの印か・値）・`outcome`（そのあとの値動き・unit つき）・`period`。突き合わせの鍵は 銘柄・日付・印。**印が付いた行を1行ずつ突き合わせる**（見出しの数字だけを作り直すのではない＝分割の直しもれのような誤りは、印の付き方に出るため）。点検①は、この形には A3・A6・A8・A9・A10 だけを当てる

### 5.2 部品① ありえない数字の点検 `result_audit.py`（根に置く・送る）

- 入力：共通の形の一覧＋道具からの補足（損切りの決まり・1度に1つだけか・金曜なし・データの抜けの割合など）
- 出力：点検の名前・当てはまった取引の数・例の取引の番号（最大5件）。**損益の合計・平均・勝率は出さない**
- 重さ：**error**（結果を書かずに止まる）／**warning**（理由を1行書けば進める）

| 点検 | 中身 | 見つけられたはずの過去の例 |
|---|---|---|
| A1 時刻の順 | 決済が建てより前・建てが合図の確定より前（先読み） | — |
| A2 損の上限 | 損切りがある取引で、損が損切りの幅の k 倍を超える（窓・週明けは市場ごとに別の扱い） | RV（−694R） |
| A3 値段・1回の動き | 銘柄ごとのありえない値段・1回の動きが市場の上限を超える | R1（+947.9%）・Yahoo の分割 |
| A4 費用 | 費用が負・下限より小さい・売りの決済に建ての時のスプレッドを使った形跡 | ST ラウンド1 |
| A5 切り替わり | NY17時（夏冬）をまたぐ取引の割合と、損益がそこに寄っているか（寄っているかどうかだけ出す） | ST ラウンド1・M5-3 |
| A6 年ごとの回数の跳ね | ある年の回数が、ほかの年の中央値の3倍超か1/3未満 | M1（MT5 の欠陥データ） |
| A7 結果の片寄り | 損益の半分超が1つの時間帯・向き・銘柄から（どこかの名前だけ出す・額は出さない） | ST ラウンド1（結果が一色） |
| A8 重複・重なり | 同じ銘柄で同じ建ての時刻が2回／1度に1つの決まりなのに重なる | — |
| A9 休みの日 | 土曜・その市場の休場日の取引／金曜なしの決まりで金曜 | — |
| A10 データの抜け | 道具が数えた抜けの割合が2%超 | 2026-11-26 の OJ5 の C（ユーロ円の約7%） |
| G1 良すぎる印 | 勝率・平均が市場ごとの目安を超える → 止めずに「数え直しが必須」の印を付ける | 7月の偽薬の件 |

- 閾値は `result_audit.py` の1か所だけ。初めの値は「過去の6件の見本を全部見つけ、今ある取引の一覧で誤報が最少」になるように較正し、較正の表を残す
- **止まったとき**：直してからのやり直しは「計算の誤りの直し」と同じ扱い（理由と直した中身を登録に追記）。損益を見ていないので、登録の誠実さは保たれる
- ⚠️ A5・A7 は「寄っているか」を出すので、結果の一部が漏れる。それでも、偽の利益のいちばん典型的な形（ST ラウンド1）なので入れる。出すのは時間帯などの名前だけで、額は出さない

### 5.3 部品② 別の書き方での数え直し `recount_compare.py`（根に置く・送る）＋手順

1. 数え直しの担当（新しいサブエージェント・Sonnet〔Claude の判断〕）に渡すもの：登録の節の文・データの置き場・共通の形の説明。データの読み込み部品（`oj_lab.load_a` など）は使ってよい〔Claude の判断＝データの誤りは①の A3・A10 が見る〕
2. **渡さないもの**：元の道具のコード・結果の数字
3. 担当は `recheck/<研究>/recount.py` を書き、共通の形の一覧を出す（元の道具のファイルは開かないと指示し、作った後に開いたファイルを報告させる）
4. `recount_compare.py` が1件ずつ突き合わせる：鍵＝銘柄・向き・建ての時刻。比べるもの＝決済の時刻・値段・出た理由・費用後（許す差＝値段 1e-6・損益 0.1pips／0.01%〔Claude の判断〕）
5. 食い違いは全部、理由を書く：
   - 元の道具の誤り → 直して数え直す（登録に追記）
   - 数え直し側の誤り → 数え直し側を直す
   - 登録の文があいまい → **成績が良く見えない側**の読みに決めて登録に追記（今までの OJ のやり方と同じ）
   - **データの版の違い**〔Claude の判断〕→ 同じ日の同じ銘柄で、読み込んだ値段（入力）そのものが違うと示せたときだけ（例＝毎日記録してきたものと、あとで取り直した Yahoo の足）。違いを示した行の数を記録に書き、残りの行で一致を見る。入力が同じなのに結果が違う行は、この理由にできない
6. 説明した食い違いを直したあとで**一致が100%**なら、「検算済み」の記録（2026-11-27 訂正＝送るファイルは1つずつ名前を書く決まりなので、研究ごとに分けず `recheck/records.json` に研究の名前を鍵にしてまとめる。点検の出力も `recheck/audits.json` にまとめる）（両方の一覧の指紋・件数・一致数・食い違いの内訳・日付）を作る。価格は入れない＝送ってよい
- **使うとき**：判定が合格側（残った・合格・前向きへ）／G1 の印が付いた／いま使っている結果の洗い直し

### 5.4 部品③ わざと壊すテストの共通の道具 `mutate_check.py`（根に置く・送る）

- 道具のファイルの一時コピーに、壊し方を1つずつ入れてテストを回す。壊し方＝比べ方（`<`↔`<=`・`>`↔`>=`）・足し引きの入れ替え・定数±1・`and`↔`or`・添字±1
- テストが気づかなかった壊し方を一覧にする。元のファイルは書き換えない
- 新しい道具の登録に「壊した数・気づかなかった数とその理由」を書く（OJ5 で手でしていたことを機械にする）
- **止める関門にはしない**〔Claude の判断〕：気づかなかった壊し方の中には、意味の変わらないものがあるため

### 5.5 関門（どこで止めるか）

| 所 | 止めるもの |
|---|---|
| 新しい道具の run | 点検①に error があれば、結果を書かない |
| `mw check`（`check_site_consistency.py`・PILLAR_PREREG を読む）※2026-11-27 訂正＝`_doctrine_check.py` は根にあり、研究の問いの帳面だけを読むので、登録の関門は `mw check` に置き、`_doctrine_check.py` には下の DOCTRINE の関門を置く | **使い始めの日より後の登録**が、結果を書く前に `result_audit` を通した記録（点検の出力の指紋）を持っていなければ error。道具のファイルではなく**登録ごと**に見る〔Claude の判断〕＝古い道具（M6・M7 の総当たりの新しいラウンドなど）で新しい登録を数えるときも点検を通す。そのとき古い道具に足すのは共通の形への変換と点検の呼び出しの数行だけ（書き換えではない）で、登録の前に足すので登録する指紋とずれない。使い始めの日より前の登録（OJ5 など）は 5.7 のとおり |
| `verified_list.py`（昇格リスト・検証済みリスト） | 判定が合格側なのに検算の記録が無い → 「🔍 数え直し待ち」の欄に置き、合格としては載せない |
| `research_map.py`（研究の地図・検証中リスト） | 同じ表示 |
| DOCTRINE.md の ✅／🏅 | 新しく足す ✅／🏅 に検算の記録の出典が無ければ error（今ある項目はさかのぼらない＝5.6 の洗い直しで見る） |
| 自動で出る合格を**使う**所（メールの絞り・EA への橋渡しなど） | 検算の記録が無い合格は使わない（下の「自動で出る合格」） |

- 固定オラクルの `_doctrine_check.py` に検査を足すのは「強める」変更。この設計書の承認をオーナーの承認とし、SESSION_HANDOFF に理由を書く

#### 自動で出る合格（2026-11-27 オーナー決定＝数え直しまで待たせる）

人の手を通さずに GitHub 側で出る「合格」も、数え直しが済むまで使わない。

| 自動で出る合格 | どこで出るか | 待たせる所 |
|---|---|---|
| シグナル研究の昇格 | `signal_lab_tracker.py` が `status=promoted` にする | メールの絞り（`generate_technical_alerts.py` の昇格エッジ限定）・`ea_bridge.py`・そのほか `status=promoted` を読んで使う所 |
| 総当たりの昇格候補（M6・M7） | `screen_judge.py` → `promotion-list.md` | MT5 の実ティックの段へ進む前 |
| 前向きの目印の合格 | 各前向きの判定 | 朝のメールや取引の決まりに足す前（足すかは元からオーナーが決める） |

- **記録は止めない**：tracker の判定・前向きの記録・総当たりの集計は今のまま毎日続ける。止めるのは「合格を使うこと」だけ
- **判定そのものは変えず、使う側で止める**〔Claude の判断〕：tracker が `promoted` にするのは今のまま（判定の履歴が変わらない）。使う側は共通の小さな関数（例＝`recheck_ok(id)`：`recheck/<id>.json` があり一致が 100% か）を通してから使う。通らないものは表示を「🔍 数え直し待ち」にする（`promotion_list.py`・`verified_list.py`・`research_map.py`・`generate_track_record_page.py`）
- **今あるもの**：使い始めの日より前に昇格した `rl_tf_adx_strong`（2026-11-07 昇格）は今のまま使い、5.6 の順番①で最初に数え直す。食い違いが見つかっても、外すかはオーナーが決める（5.6）。⇒ 入れた日にはメールの動きは変わらない（いま昇格しているのはこの1件だけ）
- **知らせ方**：`check_automation_health.py` に節を1つ足す＝数え直し待ちがあれば Issue を1件。同じものは1件にまとめ、毎日新しく立てない（知らせ疲れを避ける）。数え直しは手元のセッションで行う（データと数え直しの担当が手元にあるため）
- **期限で通すことはしない**〔Claude の判断〕：待ちが長引いても、自動では合格にしない
